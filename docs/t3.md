# T3 project interface (alpha)

For one account setup followed by automatic environment registration across devices, use [T3 Connect](t3-connect.md). The local launcher below remains available when managed registration is disabled.

The alpha includes T3 0.0.45 and Codex 0.159.0 in the Linux amd64 workspace image. T3 is the primary graphical project interface. The dashboard and CLI remain available; The optional control-host registrar is described in [clients.md](clients.md); it is separate from managed T3 Connect. Roamgate is outside this release.

An operator needs the controller CLI, kubectl configuration with project exec permission, a Ready workspace using the T3 image, and a current operator-managed model grant. Deliver the grant using the procedure in [model access](model-access.md). Project agents do not receive Kubernetes or model refresh credentials.

Run `CONTROL_NAMESPACE=your-control-namespace agent-project-controller t3 WORKSPACE`. The CLI starts T3 inside that workspace and relays it to an ephemeral IPv4 localhost port through authenticated Kubernetes exec streams (at most 16 concurrent connections). It prints the local address and the location of a private JSON file containing a one-time pairing URL. On a Linux desktop the CLI opens the pairing page automatically using a private local HTML file. For a headless terminal, open the saved URL in your browser within ten minutes. Set `APC_T3_NO_BROWSER=true` to suppress desktop launch. Treat the file as a credential; do not paste it into chat, screenshots, tickets or shell history. Keep the command running. Ctrl+C stops the server and tunnel and removes the temporary pairing files. Only one launcher may own a workspace server at a time.

T3 listens only on the worker's loopback interface. No public ingress or worker Service is created. The exec relay works with the qualified gVisor profile, where ordinary pod port-forward cannot reach the sandbox loopback socket. T3 pairing and device authentication are separate from the controller dashboard's OIDC session. The initial settings enable only Codex, through the access-only adapter. Account login, logout and refresh requests are denied. Expired or revoked grants require operator renewal; the operator procedure pauses the worker before changing a grant. T3 cannot change gVisor isolation or the project's inspecting-proxy and Cilium rules.

The repository is `/workspace/repo`. T3 state and Codex threads live under `/workspace/.apc` on the project volume. Reconnecting preserves those files; project removal deletes the owned volume. This persistence is not a disaster recovery backup. Review generated changes and use the project's scoped Git identity to propose a PR.

The initial operator CLI platform is Linux amd64. Additional platforms and providers need separate qualification. Managed multi-device access is described in the T3 Connect guide. See [release criteria](release.md) for the checks required before publishing a candidate.

## Choose the checkout and open a terminal

The environment selector chooses a sandbox. A project chooses a directory inside
that sandbox. Start the agent in the enrolled checkout, `/workspace/repo`, rather
than the sandbox home directory. A project named `home` at `/workspace/home` is
outside the project adapter's permitted working roots. Starting an agent there
is rejected; select the enrolled project and create a new thread instead.

Use Ctrl+N to choose a project for a new thread when multiple projects are
available. The project may initially be titled `repo`. An operator can rename
that existing entry through stock `t3 project rename /workspace/repo <title>
--base-dir /workspace/.apc/t3` without changing its ID or existing threads.

In the thread, Ctrl+J opens the integrated terminal on Linux and Windows;
Cmd+J is the equivalent on macOS. Check the actual environment's
Settings > Keybindings if customized. Run `pwd` and `ls -la` there to confirm
the checkout before working. A different terminal directory does not change
an existing agent thread's working root.
